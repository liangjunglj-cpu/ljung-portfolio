T.01

WASP-MCP

OPEN SOURCE · V0 SHIPPEDGRASSHOPPER × CLAUDEFOOD4RHINO
// SIMULATION · TEXT PROMPT → LIVE CANVAS
01 · SPEAK

You describe the definition in plain language. Claude resolves it against evidence-backed component knowledge — every node it knows, it knows from documentation, not guesswork.

02 · PLACE

Components land on the live Grasshopper canvas, wired and auto-organised into legible clusters — with explained notes beside each group, so the definition teaches you as it builds itself.

03 · RUN

Wasp discrete aggregation executes on the canvas — parts, rules, stochastic growth — geometry the model composed but Grasshopper computes. Nothing is faked in a chat window.

04 · SEE

Viewport capture feeds back to the model — it looks at what it made, critiques it, and iterates. The loop that makes it a collaborator, not a code generator.

Why it's different: MCPs for CAD usually generate scripts blind. wasp-mcp works on the canvas itself — the model places real components, runs real solvers, and sees real output. Published on Food4Rhino and the Rhino Package Manager; installable with one PowerShell command.

T.02

ALMOND

V0.7 RC · PYPI + RHINO PACKAGE MANAGERCLAUDE → RHINO MCPOWN STRUCTURAL SOLVER
// SIMULATION · GENERATE → SIMULATE → CRITIQUE → REGENERATE
01 · GENERATE

Claude composes in Rhino from verified parts: a library of 50 models that each carry a passport of real dimensions and clearances, and a scene ledger that remembers what is already placed, so the model queries the room instead of guessing it.

02 · SIMULATE

Since 0.7, Almond runs its own 3D frame solver inside Rhino: floor and furniture loads, Eurocode load combinations, rigid or pinned joints, buckling and sway. Karamba is now optional, not required. Gravity is still not optional.

03 · CRITIQUE

A results panel names every member, support and load case: how hard each is working, how far it bends against its limit, and a plain pass or fail. The model reads those numbers and argues with them before touching the geometry again.

04 · REGENERATE

A failing section is stepped up and the frame re-run until the checks pass: a sizing loop the model can defend line by line. AI that can show its working.

Why it's different: most Rhino MCPs give the model one power, run a script, and generation stays blind. Almond is a semantic layer: real dimensions, memory of the scene, layout validation, and a structural check that needs no extra licence. First case study: the ARCC Tower, a cable-stayed office mast with spiral stair and guy cables, validated end to end through the bridge.

01 · PROMPT → WORLD

A sentence goes to World Labs Marble; an explorable Gaussian-splat world comes back — half a million gaussians per world, cached locally as SPZ.

02 · COLLIDE

Each world gets a collider mesh, GLB props and physics, so the space isn't a picture — it has floors you stand on and walls that stop you.

03 · INHABIT

Walk it on desktop or in WebXR on Quest 3, alone or in shared Socket.IO sessions. Paired with Almond, the workflow closes: reason the geometry, then walk inside it.

04 · EVALUATE

A built-in rubric captures spatial coherence, legibility, atmosphere and tectonic failure per world — the platform is both the instrument and the output of the UROP.

Why it's different: AI-to-VR demos show you a scene; Chestnut is a research instrument that logs how AI worlds fail — hallucinated geometry, scale inconsistency, tectonic nonsense — building the failure taxonomy for AI as an architectural medium.

T.03b · RESEARCH · 2026.10

TRAINING AN IMAGE MODEL FROM SCRATCH

TEXT → FLOOR PLAN10.7M PARAMETERSONE LAPTOP GPU

Chestnut's newest branch asks what it takes to own an image model rather than rent one. A small text-to-image model, trained from nothing on an 8 GB laptop GPU, learns to draw floor plans from captions like "4 rooms, L shaped, entrance east".

The point is not a product; it is a lab you can measure. The training plans are generated by code, so every caption is exactly true, and a scorer reads each output back: is it a closed building, how many rooms, does the outline match? A three-minute run answers a question before any paid GPU time is spent.

What the numbers say so far. Words alone plateau: exact room count sits near 30% whatever the training trick. Handing the model a footprint outline is the one lever that moves it. And one honest negative: that gain does not yet carry to captions the model has never seen.

T.05

GINKGO

GAME COMPILERUE 5.8 × MCP563 TESTS GREEN
// LIVE SOLVER · CLICK TO RESEED
01 · COMPILE

One JSON intent — spaces, adjacencies, mechanics, objectives, endings — compiles into a versioned GameManifest. Ambiguity fails closed at the compiler, before an editor is ever touched.

02 · SOLVE

An explicit layout solver arranges zones and routes; a spatial analyzer scores adjacency, privacy gradient and path continuity, and weak scores return as structured revision hints that re-drive the solve. Seeded — same seed, same building, every time.

03 · REALIZE

The manifest becomes a deterministic Unreal 5.8 plan — geometry, materials, lighting rigs, atmosphere grades, CineCameras, PCG, navmesh — executed over MCP in idempotent, resumable phases with content-addressed receipts.

04 · VERIFY

Nothing is trusted. Traversal walks the building, portal clearance is measured, viewports are captured, and every mutation must return evidence before its phase is accepted. The demo game plays start → ending.

Why it's different: most "AI makes a game" demos vibe-code Blueprints and hope. Ginkgo is a compiler — design intent is validated before the editor moves, every actor is ownership-tagged and reconciled, and each world carries a seeded style card (terrain archetype, palette, daylight, atmosphere) so consecutive seeds are measurably distinct places. Newest wing: outdoor world generation — seeded terrain synthesis with layout-driven terraforming, proven live across three endorsed rounds in UE 5.8 — and now a library of six complete settlements, each compiled from a typology through Rhino into Unreal with its own terrain, kit of parts, textures and lighting. T.06

BETELNUT

MAP-FIRSTGEOSPATIALLIVE MVP
// SIMULATION · GEOJSON → SEMANTIC SYNTHESIS
01 · LOAD

Drop in GeoJSON — parcels, roads, coastlines. The map is the interface; there is no ribbon of five hundred GIS buttons.

02 · ASK

A semantic layer reads the data's meaning, so you ask in design terms — "what falls within 200 m of the shoreline?" — not in SQL.

03 · SYNTHESIZE

QGIS-like operations in the browser — buffers, overlays, spatial joins — plus traffic analysis on custom input models, currently in development.

04 · DECIDE

Results render as planning evidence — built for architects and planners, not GIS specialists, with environmental simulation on the roadmap.

Why it's different: geospatial analysis normally lives in expert desktop software. Betelnut moves the essential synthesis into a map-first browser app where the semantic layer does the GIS translation for you.
